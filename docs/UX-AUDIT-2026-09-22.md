# UX Audit — Simulasi POV 5 Role (22 September 2026)

> Ditulis oleh manager-session. Metodologi: BUKAN pengujian browser langsung (sandbox manager-session tidak punya akses ke server lokal Fakrul) — tiap role ditelusuri oleh subagent terpisah yang membaca routes → controller → view Blade secara berurutan sesuai apa yang akan benar-benar dialami user, lalu menyimulasikan reaksi sebagai user awam ("saya bingung di sini karena...", "info ini harusnya ada dari awal"). Semua temuan disertai file:line sebagai bukti, bukan tebakan.

---

## Temuan Paling Penting: Satu Bug Sistemik yang Kena ke 3 Role Sekaligus

Ini ditemukan independen oleh 2 subagent berbeda (audit Admin & audit Super Admin), keduanya sampai ke kesimpulan yang sama tanpa saling tahu — jadi confidence-nya tinggi:

**Alur "Pintu 1" (Client ajukan proyek → Super Admin ACC → masuk ke Admin) menghasilkan proyek yang setengah jalan.** `Client\ProjectRequestController::store()` hanya mengisi field administratif (nama produksi, PH, kuota, deadline, `brief_catatan`) — TIDAK PERNAH membuat baris `casting_project_classes` (breakdown kelas/karakter) atau `event_shooting_dates` (tanggal shooting). Begitu Super Admin klik ACC, proyek langsung berstatus `dibuka` padahal nol kelas & nol tanggal. Dan begitu ACC diklik, `brief_catatan` — isi kebutuhan casting yang ditulis Client — hilang dari pandangan semua orang; tidak pernah ditampilkan lagi di halaman Admin manapun.

Dampaknya kena 3 role sekaligus:
- **Client** merasa sudah menulis brief lengkap, submit, selesai tugasnya.
- **Super Admin** klik ACC dan merasa "sudah beres, tinggal Admin jalankan".
- **Admin** yang justru harus kerja dari nol: buka proyek, nemuin nggak ada kelas/tanggal, brief aslinya udah nggak kelihatan di mana pun, harus nanya manual ke Client — persis komunikasi-tidak-tercatat yang katanya mau dihindari sistem ini.

**Rekomendasi**: `ProjectRequestController::store()` minimal simpan `brief_catatan` sebagai field yang tetap terlihat di halaman edit/detail proyek Admin (bukan cuma di tabel ACC yang sekali lihat lalu hilang), dan/atau beri Admin prompt jelas "Proyek ini dari pengajuan Client, breakdown kelas & tanggal belum diisi" saat pertama kali buka.

## POV Extras

Alur: Register → Lengkapi Profil → Cari & Apply Casting Call → Nego Fee → Kontrak → Absensi → Pembayaran.

**Yang sudah bagus** (jangan diubah): registrasi langsung mengarahkan ke lengkapi profil (bukan dashboard), NIK/rekening sengaja dipisah ke tahap pasca-lolos (bukan diminta di awal — ini data-minimization yang benar), alasan tolak dini sudah tampil jelas ke Extras.

**5 masalah terurut dari paling parah:**

1. **Tanda tangan kontrak tanpa bisa membaca isinya dulu.** PDF kontrak digenerate (`ContractController::renderPdf()`) tapi tidak ada satu route pun untuk Extras stream/download PDF-nya sebelum tanda tangan (beda dengan Invoice yang punya route download). Extras menandatangani dokumen hukum/finansial tanpa pernah bisa membacanya lewat sistem.
2. **Requirement karakter (umur/gender/ciri fisik) tidak ditampilkan saat apply.** Kolom `kriteria` di `casting_project_classes` sudah dikirim ke tampilan Client tapi tidak pernah dirender di `extras/projects/show.blade.php`. Extras memilih peran "buta", bisa daftar ke peran yang jelas tidak dia penuhi, ketahuan hanya lewat penolakan belakangan.
3. **Hasil validasi absensi selfie tidak pernah disampaikan.** Tidak ada tempat manapun di UI Extras yang menampilkan status tervalidasi/ditolak, tidak ada notifikasi. Extras cuma tahu ada masalah kalau ditegur langsung di lapangan.
4. **Apply tidak dicek kelengkapan profil maupun status proyek** (`Extras/CastingProjectController::apply()`) — bisa apply dengan profil kosong total, atau ke proyek yang kuotanya sudah penuh/deadline lewat (method `menerimaPendaftaran()` yang seharusnya mengecek ini tidak dipanggil di jalur ini).
5. **Bukti transfer & tanggal pencairan honor tidak ditampilkan** di halaman pembayaran Extras — file-nya ada di database, tapi tidak ada link/gambar untuk melihatnya.

## POV Admin

Alur: Dashboard → Buat/Terima Proyek → Review Pendaftar → Nego Fee → Ajukan ke Client → Kontrak/Invoice → Kelola Akun.

**Yang sudah bagus:** kartu applicant per-kandidat lengkap dalam satu layar (foto, video, rate card, grade, catatan lapangan), kontrak & invoice dual-model berjalan rapi, prune akun mangkrak aman (ada konfirmasi, bukan hard-delete tanpa jaga-jaga).

**5 masalah terurut dari paling parah:**

1. **Rekap Margin — data finansial paling sensitif di sistem — tidak bisa diakses dari UI sama sekali.** Halaman & route-nya jalan sempurna, tapi nol link navigasi di sidebar Admin maupun Super Admin (sudah diperbaiki untuk Super Admin per audit terbaru — lihat POV Super Admin di bawah, tapi Admin belum).
2. **Brief Client hilang setelah ACC** (lihat temuan sistemik di atas).
3. **Metric "Perlu Dinego" di dashboard bukan link, dan tidak ada halaman agregat semua nego pending** — Admin harus buka tiap proyek → tiap kandidat satu-satu untuk tahu nego mana yang butuh respons hari ini.
4. **Status "diajukan ke Client" belum ada di sisi Admin** — dikonfirmasi dari kode (bukan asumsi SPEC.md Bagian AN.2), Admin cuma lihat badge status mentah tercampur di lineup, tanpa filter/mirror tampilan Greenlight milik Client.
5. **Filter lineup pendaftar cuma berdasar Grade, bukan status_partisipasi** — untuk proyek besar, Admin harus scan manual cari siapa yang masih pending nego vs siap diajukan.

## POV Korlap

Alur: Login langsung ke halaman Absensi (tidak ada dashboard ringkasan) → Validasi kehadiran di lokasi syuting (dibayangkan lewat HP, bukan desktop).

**5 masalah terurut dari paling parah:**

1. **Halaman Absensi tidak default ke "hari ini".** Dropdown proyek default ke ID terbaru, dropdown tanggal default ke `shootingDates->first()` (urutan insert, bukan tanggal terdekat). Tidak ada badge "Hari Ini". Korlap bisa validasi absensi di proyek/tanggal yang salah tanpa sadar, tanpa warning.
2. **Preview foto selfie cuma 52×52 piksel, tanpa GPS/timestamp pengambilan foto.** Melemahkan tujuan utama fitur ini (validasi kehadiran berbasis foto) — keputusan jadi modal percaya + jam server terima upload, bukan bukti lokasi/waktu asli.
3. **Tolak validasi tanpa alasan wajib diisi**, dan hasil penolakan tidak pernah tampil ke Extras (lihat temuan #3 di POV Extras — ini akar masalahnya).
4. **Tidak ada rekap/ringkasan harian atau filter "belum divalidasi naik ke atas"** — di lokasi yang ramai dengan puluhan Extras, yang masih pending gampang kelewat.
5. **Full-page reload + pesan konfirmasi muncul di atas halaman** — tiap 1x validasi, Korlap terlempar ke atas dan harus scroll ulang cari orang berikutnya. Kalau validasi 30 orang berturut-turut, ini 30x scroll ulang.

Catatan: kalender jadwal yang baru ditambahkan ternyata **tidak pernah tampil ke Korlap sama sekali** (cuma dirender untuk blok Admin, bukan blok Korlap di dashboard) — bukan soal "kurang cocok", tapi requirement itu belum benar-benar sampai ke role ini.

## POV Client

Alur: Register → Ajukan Proyek → (nunggu ACC) → Review Kandidat/Greenlight → Jadwal → Absensi → Invoice. **Perlu diingat: ini pihak LUAR JBTB, tidak bisa nanya IT internal kalau bingung.**

**5 masalah terurut dari paling parah:**

1. **Invoice & bukti absensi tidak bisa ditemukan lewat UI sama sekali**, meski otorisasi backend-nya sudah benar (`InvoiceController`, `AttendanceController::cdFotoStream`). Tidak ada satu link pun dari sisi Client ke dua halaman ini — self-service-nya nol untuk dua hal yang paling penting bagi Client (tagihan & bukti kehadiran talent yang mereka bayar).
2. **Tidak ada notifikasi sama sekali setelah proyek di-ACC/ditolak** — Client harus rajin polling manual ke halaman "Ajukan Proyek" untuk tahu progres. Tidak ada Mail/Notification untuk Client sama sekali di seluruh sistem (yang ada cuma untuk Extras).
3. **Penamaan "Casting Director" vs "Client" masih campur aduk** — halaman registrasi, judul dashboard, dan modal Greenlight ("Grade CD") masih pakai istilah lama, padahal role sudah di-rename ke `client`. Membingungkan buat production house yang tidak familiar istilah film.
4. **Status "Approved" menyembunyikan progres kontrak/produksi** — begitu Client approve kandidat, mereka merasa tugas selesai, padahal proses kontrak & produksi masih panjang dan mereka tidak pernah tahu tahapannya lagi setelah itu.
5. **"Grade CD" (A/B/C) wajib diisi saat approve tanpa penjelasan** apa artinya — tidak ada legend/tooltip di manapun.

Catatan positif: form ajukan proyek dan info kandidat di halaman Greenlight sebenarnya cukup lengkap untuk mutusin tanpa telepon Admin — masalah utamanya di *penemuan fitur* (navigasi/notifikasi) dan *konsistensi istilah*, bukan kekurangan data.

## POV Super Admin

Alur: Dashboard → ACC Proyek → Kelola Akun → Monitoring → Rekap Margin. Audit ini SEKALIGUS cross-check klaim SPEC.md Bagian AL & AN vs kode aktual.

**Klaim spec vs kenyataan — verifikasi langsung, bukan percaya teks:**

| Item | Spec bilang | Kenyataan kode |
|---|---|---|
| AL.1 — reorder dashboard total | Permintaan proyek di atas, chart dipindah ke Monitoring | ✅ **Sesuai penuh**, sudah dicek urutan render-nya persis |
| AL.2 — link Rekap Margin di sidebar | Ditambahkan ke grup Aplikasi & Monitoring | ✅ **Sesuai**, link ada dan highlight state jalan |
| AM — 4 chart lama pindah ke Monitoring | Bukan dihapus, direlokasi | ✅ **Sesuai**, chart beneran ada di Monitoring dengan data nyata |
| AN.1 — sidebar jadi 1 link "Kelola Akun" (bukan dropdown) | Sederhanakan navigasi | ❌ **Belum** — masih dropdown `<details>` isinya cuma 1 link "Kelola Staf & Client", persis kondisi yang dikeluhkan Fakrul |
| AN.1 — tab "Extras" di halaman Kelola Akun | Ditambahkan buat oversight Super Admin | ❌ **Belum ada sama sekali** — tab cuma Admin/Korlap/Client/Super Admin |

**5 masalah terurut dari paling parah:**

1. **Proyek dari ACC Client "setengah jalan"** (lihat temuan sistemik di atas — dikonfirmasi ulang dari sisi Super Admin).
2. **AN.1 diklaim tertulis di SPEC.md tapi belum dieksekusi di kode** — pola yang sama seperti insiden false-claim sebelumnya, kali ini soal fitur baru bukan bug lama.
3. **Kolom "Kode Aksi" di Log Aktivitas menampilkan enum mentah** (`SET_EXTRAS_GRADE` dkk) — minor karena ada deskripsi manusiawi di sebelahnya, tapi tetap developer-facing.
4. **Penamaan halaman "Kelola Akun" nggak konsisten** — sidebar bilang "Kelola Staf & Client", judul halaman beda lagi, spec minta nama ketiga. Tiga nama buat 1 halaman.

Hal yang patut diapresiasi: SoftDelete akun tetap aman (tidak ada hard-delete), dan bagian AL/AM yang benar-benar dieksekusi itu solid, bukan sekadar klaim.

## Ringkasan Prioritas Keseluruhan (Lintas Role)

Kalau harus pilih yang paling mendesak untuk dibenerin duluan:

1. Bug sistemik "Pintu 1" (brief hilang, kelas/tanggal kosong) — kena 3 role sekaligus, akar masalah nyata.
2. Invoice & absensi tidak bisa diakses Client lewat UI — self-service nol untuk pihak luar.
3. Extras tanda tangan kontrak tanpa bisa baca isinya — risiko hukum/kepercayaan.
4. Hasil validasi absensi tidak pernah sampai ke Extras — dead-end komunikasi yang bisa berujung sengketa lapangan.
5. Rekap Margin tidak reachable dari sidebar Admin (Super Admin sudah, Admin belum).
6. AN.1 (sidebar nested + tab Extras) — selesaikan implementasinya, jangan cuma di dokumen.

Sisanya (penamaan CD/Client, notifikasi Client, kalender belum sampai ke Korlap, dsb) tetap dicatat di atas per role, tapi levelnya lebih ke polish daripada blocking.
